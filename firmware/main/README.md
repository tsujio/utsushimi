# ファームウェア

## 実装範囲

黒背景に丸い白目と丸い黒い瞳を左右に表示し、ランダムに瞬きします。瞳を少し内向きに置いた、かわいらしい記号的な表情です。Step 1.1の表示、Step 1.2〜1.4の身体反応モデル（快不快・自動運動としての瞬き・表情）を実装しています。A/B/Cの生測定ログ・校正・接触判定、両方向の撫で検出と保持・撫でによる表情連動を実装しています。電極Aの接触・離脱判定は試作条件で実機確認済みです。撫で・表情連動と接触開始時の上方向への視線反射は、下記の12時間稼働後の確認範囲で所有者が実機確認済みです。個別条件の評価は残り、Step 1全体の完了を意味しません。

- `audio/audio_output.*`・`audio/tone.h`：短音生成・共有I2S TX/RXと独立タスク。`audio/input_rms.h` が入力RMSを計算し、入力は既定で有効、電子音試験は既定で無効。[音声テスト手順](#step-21音声テスト)を参照。
- `app_main.cpp`：起動・メモリ情報ログ、表情状態の更新、独立した表示タスク。
- `behavior/body_behavior.*`：`BodyState`、`Stimulus`、表情追従を行う `Expression` と、共通時計・イベントと接触時の視線反射を管理する `BodyBehavior`。ESP-IDF・描画に依存しません。
- `behavior/automatic_blink.*`：身体状態と独立したワイブル発生判定・不応期を管理する `AutomaticBlink`。
- `behavior/blink.*`：選択済みの単発・二連を時刻から進める `Blink` アニメーション。乱数や身体状態の管理を含みません。
- `touch/touch_sensor.*`：3電極の測定・診断ログを所有する独立タスク。保持状態と撫でイベントを身体タスクへ渡します。
- `touch/petting_detector.*`：確定接触の順序と時間から両方向の撫でを認識する、ハードウェア非依存の検出器。
- `touch/contact_detector.*`：ハードウェア非依存の起動時校正・ヒステリシス・継続時間判定。
- `board/amoled.c`：確認済みRev2.0のI2C、TCA9554のEXIO0リセット、QSPI、DMA転送。
- `display/eye_renderer.*`：ハードウェアに依存しないC++描画。`EyeState`で視線・開き具合・瞳の大きさを指定。

UI部品は不要なので、LVGLを導入せずRGB565を直接生成しています。画像の切り替えではなくパラメータで描画します。

## リポジトリ内の開発ツールを使う場合

この作業環境には `build/host-tools`、`build/utsushimi-esp-idf`（v5.5.6）、`build/utsushimi-idf-tools` を導入済みです。次のラッパーでライブラリ検索パス・ホストC++のsysroot・IDF環境を設定してmakeを実行できます。

```bash
bash bin/dev.sh test
bash bin/dev.sh build
```

`menuconfig`・`install PORT=...`・`monitor PORT=...` も同じラッパーへ渡せます。明示した環境変数 `CXX`・`IDF_PATH`・`IDF_TOOLS_PATH` は優先します。このスクリプトはツールのインストーラーではなく、`build/` のツール類はGit管理外です。別環境でツールを通常の場所へ導入している場合は以下のmake手順を使用します。

## Makefileでのビルドと書き込み

リポジトリのルートから実行します。ESP-IDF v5.5.6を使用し、既定では `~/esp/esp-idf/export.sh` を自動的に読み込みます。

```bash
make build
make install PORT=/dev/ttyACM0
make monitor PORT=/dev/ttyACM0
```

`make install` は必要なビルドを行って実機へ書き込みます。ホストPCへのインストールではありません。`make flash` も同じ動作です。`PORT` はデモで使用したポートへ置き換えてください。既存のアプリケーションは書き換わります。モニター終了は `Ctrl+]` です。

```bash
make build IDF_PATH=/path/to/esp-idf
make install PORT=/dev/ttyACM0 BAUD=460800
make menuconfig
make test
```

対象はESP32-S3に固定しています。`sdkconfig.defaults` は16MB Flash、Octal PSRAM、USB Serial/JTAGコンソールを指定します。生成済みの `sdkconfig` がある場合、defaults変更は既存値を上書きしません。`make menuconfig` で確認してください。物理容量と実機の認識結果は起動ログで照合します。

初回ビルドではコンポーネントレジストリへの接続が必要です。直接依存は `main/idf_component.yml`、解決済みの依存関係は `dependencies.lock` に記録しています。`build/`、`managed_components/`、生成される `sdkconfig` はGit管理対象外です。

## 瞬きと表示更新

瞬きと表情の仕様は[身体反応モデル](../../docs/step1-body-behavior.md)を正とします。瞬きは身体状態から独立した自動運動で、ワイブル分布に従って発生します。時間定義・状態更新・入力検証規則も同文書に集約しています。

振る舞いは10msごとに時刻を確認し、待ち時間を内部に持たず開き具合を返します。表示タスクには長さ1のキューで最新状態のみ渡すため、古いフレームが溜まりません。DMA待機は表示タスクに限定し、将来の入力処理と独立させています。描画・転送が遅れた場合は途中のフレームを省略します。目の状態が変化したときだけ描画し、表示は30Hz（約33.3ms周期）を目標にします。目標値は `display/frame_timing.h` の `kDisplayFps` で管理します。起点からの絶対時刻で表示期限を計算して端数を保持し、RTOSのtick丸めを累積させません。処理終了時に過ぎた表示枠は飛ばし、次の期限まで表示タスクだけを待機させてから最新状態を受け取ります。身体更新・タッチ検出・撫で判定の周期と、経過時間に基づく瞬き・表情の速度・継続時間は変更しません。実測値は `eyes_perf` ログの `render_avg`（描画）、`transfer_avg`（転送待ちを含む）、`work_max`（1フレーム処理の最大時間）にマイクロ秒で表示します。アイドル時間を除いた処理時間であり、パネルの実測FPSではありません。目標フレーム時間は約33,333µsで、ログの `budget` も目標値から算出します。これを超えると目標周期に間に合いません。30fpsでの実機の滑らかさ・実効更新レート・タッチ応答性は未検証です。

通常は丸い白目と瞳を表示します。閉眼中は白目を縦に閉じ、黒い瞳をその輪郭でクリップします。閉じ切ったときは黒背景になります。初回だけ背景全体を消去し、その後は両目と目の間を含む固定矩形を更新します。両目をバッファへ描き終えてから1回の描画要求で転送します。円の平方根は輪郭の1pxだけに限定し、ほかは二乗距離と行・列ごとの事前計算で判定します。快のまぶた曲線は横座標ごとに1回だけ平方根を計算します。

両目をまとめた転送によって描画途中の状態や左右更新の時間差を抑えます。パネルのTE信号に同期していないため、画面走査とのずれによるティアリングを完全に除去する保証はありません。ちらつく場合は、処理時間ログと実機映像を基に切り分けます。

## 快の表情

ユーザーによる実機確認済みの、上下の弧を揃えたまぶた形状を採用しています。[形状と追従の仕様](../../docs/step1-body-behavior.md#採用した快のまぶた形状)を参照してください。

実際の身体状態から表情を更新し、瞬きを継続します。電極Aの接触が保持刺激となり、快が増すと目を細めます。ホストテストでは意味イベントを注入して検証します。

上下のまぶたは同じ楕円弧を上下移動して作り、細目では目尻側を少し持ち上げます。円形の白目と瞳のクリップを維持します。外周では元の円によるクリップが残るため、端の厚みまで一定とは限りません。通常・心地よいの2状態をヒステリシスで選び、開眼率を有限時間で補間します。閾値・目標値・遷移時間は[Expression仕様](../../docs/step1-body-behavior.md#expression快状態の表情)を参照してください。

`make test` は通常・最大快・微小な変化・上下の弧の間隔・視線端・瞳サイズ変更・実際の瞬き行動での消去と復帰・快の自然減衰を検証します。自動運動の確率・不応期・平均開始間隔も検証します。転送矩形・DMA方式・表示ドライバーは変更していません。実機の処理時間は `eyes_perf` ログで確認してください。ホスト測定では新形状は通常描画の約1.2倍でしたが、ESP32上の描画時間は未測定です。

## 表示初期化の根拠と差分

ユーザーが表示成功を確認したローカル公式サンプル：

`~/esp/ESP32-S3-Touch-AMOLED-2.41-V2/02_Example/ESP-IDF/09_LVGL_V9_Test`

基板定義・初期化コマンドは、Waveshare公式リポジトリのコミット `0eaf16cfae3440d445f2b6caa71e94065094551f` の `components/main_config/main_config.h` と `components/lcd_bsp/display_bsp.c` を根拠にしています。[公式ソース](https://github.com/waveshareteam/ESP32-S3-Touch-AMOLED-2.41-V2/tree/0eaf16cfae3440d445f2b6caa71e94065094551f/02_Example/ESP-IDF/09_LVGL_V9_Test)。

- ネイティブ座標450×600に、論理座標600×450をソフトウェアで反時計回り90度回転して送ります（native_x = logical_y、native_y = 599 − logical_x）。パネルを横向きに置いてください。実機の取り付け方向との一致は確認してください。
- 公式のQSPI 40MHz、RGB565、コマンド表、EXIO0のリセット順序を維持します。画面タッチ用EXIO1は操作しません。
- 初期化時の輝度を0にして、背景と目を描いた後に約50%へ上げます。
- RGB565は上位バイトから送信します。内部DMAバッファは174×174画素の2枚分、121,104バイトで、転送完了後に再利用します。初期化失敗・転送タイムアウトはログを伴って停止します。
- 起動時のリセット待機は表示タスク内に限定します。
- Wi-Fi、BLE、画面タッチ、IMU、RTC、microSDは初期化しません。表示リセットに必要な共有I2Cバスは使用します。

## 電極Aの初期動作確認

Step 1.3では外部電極A/B/Cを測定し、保持と両方向の撫でを身体反応へ接続します。B/Cは各510Ωを介してハードウェア文書の割り当て表どおりに配線してください。配線の正本は[ハードウェアの電極A配線手順](../../docs/hardware.md#step-13初期確認電極aだけの配線)です。画面タッチのFT6336とは別の機能です。

### ドライバーと処理構成

ESP-IDF **v5.5.6** の新ドライバー `esp_driver_touch_sens` / `driver/touch_sens.h` を使用します。実際の同バージョンのヘッダー、ドライバー実装、および[公式touch_sens_basicサンプル](https://github.com/espressif/esp-idf/tree/v5.5.6/examples/peripherals/touch_sensor/touch_sens_basic)と[共通設定](https://github.com/espressif/esp-idf/blob/v5.5.6/examples/peripherals/touch_sensor/touch_sens_examples_common/touch_sens_example_config.h)を参照しています。旧 `touch_pad` APIとは混在させません。

- 独立した `touch_raw` タスク（優先度5、スタック4096バイト）がコントローラーとA/B/Cの3チャンネルを所有します。表示タスクは優先度4のままです。
- 50ms周期で `touch_sensor_trigger_oneshot_scanning` を実行し、完了後に `touch_channel_read_data(..., TOUCH_CHAN_DATA_TYPE_RAW, ...)` で読みます。最初の成功3測定はウォームアップとして捨てます。
- 測定待ちは専用タスク内だけで、3チャンネル全体に100msのタイムアウトを設けます（スケジューリングによる超過はあり得ます）。描画より優先度を高くし、ドライバーのチャンネル間の再開遅延を抑えます。走査中の待機はドライバーがCPUを譲ります。過去の測定をまとめて再生しません。コールバックやISR内ではログを出しません。
- 測定設定は公式V2サンプルと同じ充放電500回・電圧範囲0.5〜2.2V・充放電速度7を初期値とします。測定感度の最終調整値ではありません。
- ドライバー内のフィルターと接触イベントは使いません。API構造体の `active_thresh` はゼロ初期化のままで、接触判定には使用しません。ソフトウェア側の判定は下記の暫定設定で行います。
- 初期化失敗は失敗したAPI名・エラー名をログに出し、診断だけを終了します。チャンネル固有のエラーは `touch_a` / `touch_b` / `touch_c` で識別します。測定・読み取り失敗は正常値を出さず、次の周期で再試行します。`ESP_ERROR_CHECK` による本体停止は行いません。
- 測定値をBodyBehaviorやEyeRendererへ渡しません。基準値・接触状態・ウォームアップ・継続時間・ログ間隔は各電極が独立して保持します。走査全体の失敗は全電極の欠落、読み取り失敗は該当電極だけの欠落として扱います。判定には走査完了時刻を使います。

### 接触判定（暫定・電極A単独で実機確認済み）

`touch/contact_detector.h` の `ContactSettings` に共通の暫定調整値を集約しています。Aで試した設定をB/Cにも暫定適用します。基準値は各電極で独立して取得し、B/Cの感度は実測で判断します。基準値は起動後の成功40測定以上・約2秒以上の平均です。最初の3成功測定を捨てた後に校正します。**起動から `event=calibrated` までは触れないでください。** 校正区間の最大値−最小値が500を超える、または0を含む場合は警告して再取得します。測定エラー・150msを超える欠落も校正をやり直します。

接触・離脱の50msデバウンスは実機評価前の暫定値です。短い接触ノイズを抑えながら応答を早める設定です。

- 接触：`raw - baseline >= 1000` が50ms継続。
- 離脱：`raw - baseline <= 600` が50ms継続。
- その間は確定状態を維持します。条件を外れた値・測定エラー・150msを超える欠落で継続時間判定を中断します。欠落自体を離脱とは扱いません。
- 校正後は電極ごとに、接触状態によらず10秒間安定した測定値へ追従します。条件・制限は[基準値の追従](../../docs/step1-body-behavior.md#基準値の追従暫定)を参照してください。起動時の再校正が必要な場合は、手を離してRESETします。
- 通常ログは250ms周期、校正完了・接触開始・終了は直ちにログへ出します。身体タスクは最新の確定接触状態の変化を `touch_started` / `touch_ended` に変換してBodyBehaviorへ渡します。

暫定閾値は初期測定での約2,000以上の増加と非接触時の揺れを参考にしたものです。試した短い接触は操作と一致しています。環境・電極条件を変えた感度は未検証です。安定して触れたまま起動すると、その値を非接触基準として採用する可能性があり、raw値だけでは識別できません。`state=calibrating` 中のbaseline/deltaは判定用の有効値ではありません。

### 3電極から表情への接続

`PettingDetector` が接触順序を意味イベントに変換し、身体タスクが保持と撫でを `body.input()` に渡します。判定条件・キュー・欠落の扱いは[タッチ入力と撫で判定](../../docs/step1-body-behavior.md#タッチ入力と撫で判定暫定)を正本とします。瞬き・身体モデル・描画計算は維持しています。

3電極とも校正完了後、いったん全部離し、A→B→Cを約0.4〜1.5秒でなぞってください。最後まで手のひらで覆わず、指を移動させます。毎回全電極から手を離し、逆方向も試します。ログ例（実測結果ではありません）：

```text
touch: elapsed_ms=... event=petting_detected direction=A->B->C
body: petting_detected direction=A->B->C valence=...
```

撫で1回で快が加算されて目が細まり、離した後にゆっくり中立へ戻ることを確認します。3枚同時に手を置いても撫でログが出ないこと、保持中も瞬きが続くことを確認してください。保持状態の変化は `body: touch holding=1/0` で確認できます。保持だけでも徐々に快が増えるため、表情変化だけで撫で成立を判断しないでください。速すぎる撫では接触の50ms確認を満たせず取り逃がす可能性があります。

### 書き込み・測定の基本手順

1. 電源を切り、ハードウェア文書に従って電極A/B/Cを配線します。机上で板とワイヤを固定してください。
2. USB-CをPCへ接続し、リポジトリのルートから実行します。ポート名は実際のデバイスに合わせます。

   ```bash
   make install PORT=/dev/ttyACM0
   make monitor PORT=/dev/ttyACM0
   ```

   WSLでUSB接続が必要なら、対話可能な端末で `bash bin/connect-esp32.sh` を実行します。sudoのパスワード入力には端末が必要です。モニター終了は `Ctrl+]` です。

3. 起動時の `touch_a` / `touch_b` / `touch_c` 設定ログと `Warmup complete` を確認し、3枚とも手を離したまま各電極の `event=calibrated` を待ちます。表示と通常の瞬きも続いていることを確認してください。
4. 指や手を電極・ワイヤから離して10秒程度観察し、`raw` の範囲と揺れを記録します。
5. 板の表面の、裏側の電極Aに対応する位置へ指を置き、5〜10秒保持します。銅箔へ直接触れず、配線や基板も動かさずに測定してください。
6. 手を離して10秒観察し、接触・非接触を数回繰り返します。B/Cでも同じ試験を行い、触れていない隣の電極が反応しないことも確認します。接触ごとに `touch_started`、離脱ごとに `touch_ended` が各1回だけ出るか確認します。
7. 軽い接触、30秒程度の長押し、非接触で1分以上放置を試します。長押し中に離脱が出ないこと、放置中に接触が出ないこと、保持で表情が変化し、瞬きが継続することを確認してください。閾値付近で揺れる場合はraw・baseline・deltaを保存します。

ログの形式（山括弧内は説明用のプレースホルダーで、実測値ではありません）：

```text
I (...) touch_a: elapsed_ms=<ミリ秒> raw=<測定カウント> baseline=<基準値> delta=<差> state=<idle/touched/calibrating> event=<none/calibrated/touch_started/touch_ended>
E (...) touch: elapsed_ms=<起動からのミリ秒> scan failed: ESP_ERR_TIMEOUT (0x107)
```

`raw` は容量のpF表示ではなく、充放電にかかる時間に対応したカウントです。ESP32-S3では通常、接触で容量が増えると値が増える方向ですが、絶対値と変化量は実測で確認します。エラー例は形式の説明であり、発生を予測するものではありません。rawを含む通常ログは測定API成功時のみ出力します。接触判定の正確性は実機で照合してください。

### 値が変化しない・不安定な場合

- `touch_a` が出ない場合は起動ログとタスク作成・初期化エラーを確認し、書き込んだファームウェアとポートを確認します。
- エラーが出る場合はAPI名・エラー名と起動ログを記録します。初期化に失敗した場合は原因を解消してRESETします。
- 電源を切って、J8の向きと3番、抵抗両端のブレッドボード接続列、銅箔と金属ピンの接触を確認します。テスターがあればGPIO側ワイヤから電極まで約510Ωとなるか確認します。

## ホスト側テストとプレビュー

`make test` はESP-IDFや実機なしで、既存の描画検証、瞬きの時系列、身体状態・刺激・確率・表情合成・不応期・身体状態と瞬きの独立性を検証します。同一シードとイベント時刻では、呼び出しの分割が異なっても内部状態と行動時刻が一致することを確認します。シミュレーションは下記条件で自動実行します。

### 5項目の設定とイベント注入

`behavior/body_behavior.h` の `BehaviorParameters` が5項目の既定値を持ちます。意味と初期値の一覧は[仕様書のパラメータ表](../../docs/step1-body-behavior.md#調整可能な振る舞いパラメータ)に集約しています。実機では `app_main.cpp` の `parameters` を変更して再ビルドします。時間の単位はすべて秒です（150msは `0.150f`）。例えば：

```cpp
utsushimi::BehaviorParameters parameters;
parameters.holding_sensitivity = 0.03f;
ESP_ERROR_CHECK(parameters.valid() ? ESP_OK : ESP_ERR_INVALID_ARG);
utsushimi::BodyBehavior body({[](void *) { return esp_random(); }, nullptr}, parameters);
```

入力範囲と正の待機時間の制約は[発生確率モデル](../../docs/step1-body-behavior.md#発生確率モデル)を参照してください。`app_main.cpp` は構築前の `parameters.valid()` を `ESP_ERROR_CHECK` で検査します。ライブラリを直接利用する場合も検査し、既定値へのフォールバックは `used_default_parameters()` で検出してください。実行中の設定変更・保存UIはありません。

ホスト側では固定シードの乱数コールバックを注入します。テストの `Rng` は非ゼロシードのxorshift32です。実機は `esp_random()` を使用しますが、暗号用途には使いません。乱数コールバックは必須で、一様な32bit値を返す契約です。

```cpp
body.advance(elapsed_us);  // 前の入力から現在まで進める
body.input(utsushimi::BodyEvent::touch_started);
body.input(utsushimi::BodyEvent::petting_detected);
// 継続保持中はadvance()だけで快方向の刺激が続く
body.input(utsushimi::BodyEvent::touch_ended);
eyes.gaze_y = body.touch_gaze_offset() * utsushimi::kEyeRadius * eyes.pupil_size / utsushimi::kGazePixels;
eyes.openness = body.blink_openness();
eyes.upper_lid = eyes.lower_lid = 1 - body.expression_openness();
```

イベントは呼び出し時点のモデル時刻で適用します。同じタスクから呼ぶAPIであり、スレッドセーフではありません。3電極の保持状態と撫でイベントを身体タスクがこのAPIへ渡します。描画側へセンサー値は渡しません。

### 描画の速度最適化と実機比較

描画ファイルのみ `-O2` でコンパイルし、完全に白い内部画素はRGB565の白を直接書きます。

```bash
make monitor PORT=/dev/ttyACM0
```

monitorの開始が間に合わなければRESETします。RESET／電源再投入のたびに1回だけ送信し、入力有効時は、その後も無音TXとマイク取得を継続します。入力無効時のみI2Sクロックを止めます。長さは生成するPCMのサンプル数で指定し、実際の送信開始・終了間隔には無音区間とスケジューリング待機を含みます。設定時間と壁時計の間隔が完全に一致する保証はありません。

初回は振幅1%から確認し、必要な場合だけ少しずつ上げます。実機確認済みの条件は下記を参照してください。振幅は音響出力電力の制限値ではなく、GAINはソフトウェアから操作しません。`Tone start` と `Tone sent` はソフトウェアの送信経路のログで、出音の証明ではありません。`Tone failed`、初期化エラー、brownout/reset、タッチ走査エラーがないことを確認します。

試験終了後は音声テストを無効にして再ビルド・書き込みすると、通常の無音動作に戻ります。タッチや撫でのイベントに発声は接続していません。

### 出力モジュール

`audio/audio_output.h` の `start_audio_output()` を起動時に一度呼び、完了後に `play_tone(hz, duration_ms, volume)` を利用します。要求はコピーされ、呼び出し元でDMAを待ちません。周波数20〜20000Hz、長さ1〜2000ms、振幅0〜0.1を受け付けます。実行中1件と待機1件まで扱い、満杯は `ESP_ERR_TIMEOUT`、不正値は `ESP_ERR_INVALID_ARG`、未初期化・重複初期化は `ESP_ERR_INVALID_STATE` を返します。初期化は複数タスクから同時に呼ばない契約です。

新I2Sドライバーのstandardモードで48kHz・32bit符号付きPCM・左右2スロットを送信します。65要素の1/4周期サイン表、線形補間、32bit位相の加算で5msずつ生成し、送信ループでは三角関数や倍精度演算を使いません。左右は同値で、両端には5msのフェードを入れます。長い波形配列や外部音声ファイルは使いません。

音声の初期化・送信・入力タスクは優先度0で、身体更新（1）、表示（4）、タッチ（5）より低くします。I2S送信待機の上限はブロックごとに1秒で、送信データが間に合わない場合はDMAからゼロを送ります。初期化・タスク作成・送信のエラーはログに出し、身体ループを停止しません。ギャップのない音声再生や低遅延の長時間ストリーミングは今回の検証対象外です。

### 音声出力の検証状況

**所有者確認済み：** 音声配線とタッチ配線を離した配置で、440Hz・2000ms・振幅50/1000（5%）の出音を確認しています。同じ試行のログでは、送信中のC保持判定、身体更新（約500msあたり50回）、走査（同10回）、表示要求・転送完了・瞬き開始が継続しています。送信終了後の離脱も身体に反映されています。これは単一の試作条件での確認です。

Cのrawは送信前約48,020、送信中約47,800〜47,900で、保持判定解除はありません。小さな測定値低下は残り、干渉が完全に解消したとは扱いません。近接した配線配置では送信中のraw低下によって接触判定が解除される条件があります。[配置・電気的制約](../../docs/hardware.md#タッチとの共存に必要な配置)を維持し、閾値や校正を変更して影響を隠さないでください。

**Step 2.1のソフトウェア検証：** TXのみの構成でESP-IDF v5.5.6の通常・音声テストのビルドを確認しています。`make test` は既存の描画・瞬き・身体反応・接触・撫での回帰試験と、波形の20／440／1000／20000Hz・1／200／2000ms、参照サイン波との誤差、振幅・無音・両端ゼロ・ブロック境界の位相連続性を確認します。参照波形との許容誤差はピーク振幅の0.03%＋整数丸め4以下です。ホスト試験は物理I2S信号や電気的干渉を検証しません。

**未確認：** 200ms・初期振幅1%での聴感、発音中の新規接触・離脱・撫で反応、繰り返し・長時間・電源や配置を変えた再現性、実際の音圧・電力・発熱・起動停止ノイズです。Step 1の既存の実機確認を、この音声追加版の全機能確認に流用しません。

### 同時動作の確認と進捗診断

1. 音声テスト無効で、通常の目・瞬き・個別接触・視線反射・両方向の撫でと表情復帰を確認します。
2. テストを有効にし、校正完了までは全電極から手を離します。発音前からCを保持し、保持判定と表示の継続を確認します。その後、別の試行で発音中の新規接触・離脱・撫でを試します。
3. 同じ電源・配線・ログ設定で `eyes_perf`、走査失敗／復旧、`body: Update delayed`、rawの変化を比較します。変化が大きい場合は振幅0の送信、電源を切ってアンプを完全に切り離す条件と比較します。

進捗診断を有効にすると、`Tone start` に実行時の優先度、`audio: Progress` に約500msごとと要求終了時の処理回数を出します。`body_updates`（身体更新）、`display_requests`（表示要求）、`display_completed`（両目の転送完了）、`touch_scans`（成功した走査）は表示された `window_ms` 内の回数です。状態が変化しない間は表示要求を送らないので、表示回数0だけでは停止と判定しません。

カウンターは整数の加算・読取りだけを短いクリティカルセクションで保護し、制御には使用しません。同時点の厳密なスナップショットではありません。診断無効時はカウンターの加算・読取りと進捗ログを無効化します。

## Step 2.2：音声入力とRMSログ

[確定配線と電気的条件](../../docs/hardware.md#step-22inmp441マイク1個)を確認します。`make menuconfig` の `UTSUSHIMI → Continuously log INMP441 left-channel RMS` は既定で有効です。既存のローカルsdkconfigでも設定を確認してから `make build`、`make install PORT=/dev/ttyACM0`、`make monitor PORT=/dev/ttyACM0` を実行します。

起動約5秒後に音声を初期化し、48kHzの左4800サンプル（100ms）ごとに `audio_input: rms=... dBFS=...` を出します。ログの時刻間隔はスケジューリングで変動します。32bitワードの上位24bitを符号付き値に復号し、2^23で正規化、Welford法で窓内の平均を除去した母分散の平方根を計算します。RMSはフルスケールに対する無次元比、dBFSは20log10(RMS)、ゼロは-infです。音圧dB SPLではなく、DC成分も音量に含めません。右スロットと下位8bitは使用しません。

1. 電極から手を離して起動し、校正とRMSログの継続を確認します。静かな環境、声、拍手の順に値を比較し、固定値・ゼロのままでないことを確認します。静かなときもマイクのノイズがあるためゼロになる保証はありません。ゼロだけでは取得成功と判断しません。
2. 既存の単発電子音テストを有効にし、発音前・中・後にもRMSが継続することと、従来どおり出音することを確認します。自分の電子音もマイクへ入ります。振幅・時間はStep 2.1の手順に従います。
3. 目・瞬き・個別タッチ時の上目・両方向の撫でと笑顔を確認します。既存のraw/baseline/delta、走査失敗／復旧、`eyes_perf`、音声試験の進捗診断を維持しています。同じ配線・電源で入力有効／無効を比較してください。入力無効かつ音声試験無効ならI2Sは起動しません。常時クロックによる干渉を閾値変更で隠さないでください。
4. 長時間運転し、`Read failed`（DMA受信キューあふれを含む）、`Silence failed`、`Tone failed`、走査エラー、resetの有無と、空きヒープ・タスクスタック余裕をデバッガ等で比較します。エラーのないログだけでメモリリークなしと断定しません。

入力のエラー・受信キューあふれでは集計窓と当該ブロックを破棄し、不連続な音声を1つのRMS窓に混ぜません。あふれだけなら待機せず読み進め、APIエラー・空読取り・不正なバイト数の場合だけ20ms待ちます。エラーログは最大毎秒1回です。入力・出力タスクは優先度0、各DMAブロックは5ms、入力有効時のDMA領域は各方向8枚・40ms分であり、高負荷で取得が欠落する可能性は実機評価が必要です。自動再初期化、録音、認識、音声由来の身体イベントは実装していません。

### スタックと検証状況

入力タスクのスタックは8192バイト、送受信のPCM作業領域は各1920バイトのタスク専有の静的領域です。浮動小数点ログを含む入力処理の余裕を確認するため、読取りループで約10秒ごとに `Stack minimum free: ... bytes` を出します。これはタスク開始からの最小空き量であり、減少だけでは継続的なメモリ消費やリークを意味しません。

**ソフトウェア検証：** `bash bin/dev.sh test` で24bit復号・下位bit無視・DC除去・既知サイン振幅・最大振幅と既存の回帰試験が成功しています。ESP-IDF v5.5.6で入力のみ（電子音試験無効）、入力と電子音試験の併用、入力無効のTXのみ（進捗診断有効）の3構成のビルドが成功しています。構成別の検証には独立したSDKCONFIG・ビルドディレクトリを使用し、実機確認用の `firmware/sdkconfig` は維持しています。

**所有者による基本動作確認：** 静かな区間より発声時のRMSが増え、発声終了後に戻ること、3回の拍手に対応するピーク、起動時の電子音の出音、瞬き・接触時の上目・撫での笑顔を確認しています。確認した電子音設定は440Hz・2000ms・振幅50/1000で、進捗診断は無効です。

提供ログ（ELF SHA256先頭 `241f9a1e1`）で確認できる範囲：

- 電子音の送信前後をまたいで約100msごとのRMSが継続。低い区間は概ね0.0005〜0.0015、発声時は概ね0.008〜0.014、拍手は0.031／0.041／0.051へ上昇しています。
- 起動後約12分の抜粋でもRMS・タッチ走査・身体更新・描画が継続。A/B/Cの接触・離脱とA→B→Cの撫でイベント、Bodyのvalence=0.362・openness=0.573への反映中も取得が続いています。
- 提示区間に受信エラー・スタックオーバーフロー・再起動はありません。入力スタック最小空きは初期6124バイト、約12分時点で5916バイトです。

**既知の制約・未確認事項：**

- 音声開始後のタッチ測定値変化は残っています。配置の比較用ログではA/Bのdeltaが主に約-200〜-350、Cは主に約-200です。別の配置・校正条件ではCが約-1000になる区間もあります。再起動・再校正を伴う比較のため、配線接触だけを原因とは断定しません。音声配線と電極配線を離して固定し、閾値変更で干渉を隠さないでください。
- 常時クロック構成での個別感度、長い保持、両方向の撫での検出精度、配置・電源を変えた再現性は未評価です。
- 周囲のファン音によるRMS上昇は疑われますが、位置だけを変えた対照試験では未確認です。起動直後の大きなRMSは過渡応答や音響入力を切り分けておらず、無音評価から除外します。
- 起動からの全ログ・ヒープ推移・30分以上の連続動作・故障経路は未確認です。メモリリークなしとは扱いません。Step 2.1の電源・GAIN/SD・音量等の未検証項目も維持します。

RXのslave切替警告はTX/RXの共有クロック構成に伴う通知です。`Tone sent` は送信経路のログで、出音そのものの証明ではありません。追加試験は上記の手順で、既存機能と音声取得の継続、残るタッチ測定値変化とメモリ余裕を確認します。
